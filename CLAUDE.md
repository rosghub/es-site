# Editing website content

This file is for editors working in the `rosghub/es-site` repository. If you
are working in the `estimate-sync` monorepo, where this folder is
`apps/web/content/`, ignore this file and follow the monorepo's `AGENTS.md`.

Read this whole file before you change any page on estimatesync.com.

Your job is to change the words on existing pages. You are not redesigning,
restructuring, or rebuilding anything. If a request seems to need more than a
text change, stop and describe what's needed in the pull request instead.

## Where the content lives

Every editable page is a Markdown file in one of these folders:

- `paint-estimate-app/` holds product pages and articles.
- `docs/guide/` holds how-to guides.
- `docs/reference/` holds reference pages.

The file path matches the page URL. For example,
`estimatesync.com/paint-estimate-app/teams` is
`paint-estimate-app/teams.md`.

The landing page at `estimatesync.com/paint-estimate-app` is not in this
repository and is out of scope.

## What to edit on each page type

To tell the page types apart, look at the frontmatter. That's the block
between the `---` lines at the top of the file.

**Product pages** have `pageClass: product-page`. The body is only
`<ProductShowcase />`, so leave it alone. All visible text is in the
`product:` frontmatter. You may change these values:

- `hero.lead`
- `heading`, `body`, and `bullets` in each entry under `sections`
- `imageAlt` anywhere
- `label` and `description` in each entry under `relatedLinks`

For long paragraphs, keep the `>-` style that the page already uses.

**Articles** have `pageClass: article-page`. You may change the Markdown text
in the body and the text between `<ArticleQuote>` and `</ArticleQuote>`. When
you edit an article, set `updated: "YYYY-MM-DD"` in the frontmatter to
today's date. Add the field if it isn't there.

**Guides and reference pages** have no `pageClass`. You may change the
Markdown text in the body.

On every page type, you may also change `title` and `description` in the
frontmatter. On articles, guides, and reference pages, keep the `# Heading`
at the top of the body the same as `title`.

## Never change

- `layout`, `pageClass`, `sidebar`, `aside`, `outline`, `prev`, `next`,
  `intended URL`, `publish status`, `source packet`, `audience`,
  `review status`, `source file`, `generated by`, `author`, `date`, or
  `ogImage`.
- Image paths, unless the request asks you to add or replace an image. That
  includes `image`, `src`, and `banner` values. See "Adding images" below.
- Link targets (`href` values and Markdown link URLs), unless the request
  names the new target. Every internal link must point to a page that
  exists, or the build fails.
- Component tags such as `<ProductShowcase />`, `<ArticleByline />`,
  `<ArticleBanner ... />`, `<ArticleCta />`, and `<ArticleScreenshot ... />`.
  Don't add, remove, move, or reconfigure them.
- Anything in `.vitepress/` or `scripts/`.
- Existing files in `public/`. Add new images there only as described in
  "Adding images," and never edit, replace, or delete an existing one. Other
  pages and the app may use it.
- `package.json`, `package-lock.json`, `.gitignore`,
  `.public-docs-manifest.json`, or this file.
- Any other file outside the three content folders and `public/`.

Don't create, delete, rename, or move pages. If the request needs any of
these, say so in the pull request, and a developer will handle it.

## Adding images

Every image needs resized copies, because the pages ask the browser to pick a
width. `scripts/generate-screenshot-srcset.sh` makes them. It writes
`<name>.png` and copies named `<name>_288w.png`, `<name>_576w.png`,
`<name>_864w.png`, and `<name>_1152w.png`.

1. Get the source image as a file. If the user attached it in chat and you
   can't find it on disk, ask them to upload it on GitHub into an `incoming/`
   folder on your branch, then pull the branch.
2. Pick a new name of lowercase letters, numbers, `-`, and `_`, such as
   `estimate-review`. Never reuse a name that already exists in `public/`.
3. Run the script. It needs ImageMagick. If `magick` and `convert` are both
   missing, install it first with
   `apt-get update && apt-get install -y imagemagick`.
   - Phone screenshots:
     `bash scripts/generate-screenshot-srcset.sh <file> public/screenshots <name>`
   - Wide banners:
     `bash scripts/generate-screenshot-srcset.sh <file> public/banners <name>`
4. Commit `<name>.png` and every width copy the script wrote. Delete the
   source file and `incoming/` so they aren't committed.
5. Point the page at `/screenshots/<name>.png` or `/banners/<name>.png`,
   never at a width copy. The page adds the copies itself.
6. Write alt text that describes what the image shows: `imageAlt` in product
   page frontmatter, or `alt` on a component.

Where each kind of image goes:

- **Phone screenshots** go in `public/screenshots/` and must be at least
  1152 pixels wide. The existing ones are 1440 pixels wide. The pages always
  ask for all four width copies, and the script skips any width larger than
  the source, so a narrower image shows up broken. If the source is too
  narrow, stop and say so in the pull request.
- On product pages, a phone screenshot can be the `image` of `hero` or of an
  entry under `sections`.
- In articles, a phone screenshot goes in
  `<ArticleScreenshot src="/screenshots/<name>.png" alt="..." />`.
- **Article banners** go in `public/banners/` and use
  `<ArticleBanner src="/banners/<name>.png" alt="..." :width="W" :height="H" />`,
  where `W` and `H` are the source image's size in pixels. Get them with
  `magick identify -format "%w %h" <file>`.
- Wide images such as laptop or browser screenshots don't fit product page
  sections, which expect phone screenshots. If the request needs one there,
  say so in the pull request instead.

Check every new image in the Cloudflare preview at a narrow and a wide window
size.

## How to make an edit

- Change only the text the request names. Leave the other paragraphs,
  headings, and pages as they are, even if you would word them differently.
- Never rewrite a page from scratch or reorder its sections. An edit should
  produce a small diff.
- Keep the existing Markdown structure: heading levels, lists, and blank
  lines between blocks.
- Some pages say `"generated by": "scripts/public-docs-pipeline.js"` in their
  frontmatter. That script isn't in this repository. Ignore the note and edit
  the page directly.

## Words the live site rejects

The build that publishes estimatesync.com rejects a page whose body contains
any of these, in any capitalization:

- backend, callable, handler, repository, Firestore, function, source code,
  inspected source
- PaintScout
- Evidence:, author-facing, do not publish
- `.dart`, `.tsx`, `test.cjs`, `flatCost`

The preview build in this repository doesn't check for them, so a page can
look fine in the preview and still be rejected later. Check your changes
against this list before you open the pull request. "Function" is the one
most likely to slip in. Write "purpose" or "role" instead.

## Opening the pull request

- Never push to `main`. GitHub rejects it. Work on a branch and open a pull
  request.
- Start the commit message with `ui:`, for example
  `ui: reword the pricing article intro`.
- In the pull request description, list each page you changed, with one
  sentence per page on what changed.
- Cloudflare Pages builds a preview of every branch and posts its link on the
  pull request. Open the link and check each page you changed.
- If the preview build fails, read the error and fix the page. A link to a
  page that doesn't exist is the usual cause.
